# 算法说明：A* 路径规划与冲突检测

> 代码位置：`algorithm-service/app/algorithms/`
> 接口契约：`docs/03-api-contract.md` 第 4 节

## 1. 为什么用 A* 而不是直接连线

无人机不能直线飞行的原因有三个，按重要性排序：

1. **禁飞区**：机场净空区、军事管制区，绝对不可进入；
2. **限飞区**：有时间/高度限制的区域（本项目用高度区间表达）；
3. **绕行成本**：绕路会多耗电，而电量是最稀缺的资源。

MVP 用 A*（栅格图搜索）就够了：实现简单、结果可解释、任何时刻都能回答"为什么绕这一侧"。
当约束变多（多机协同、动态障碍、时序窗口）时再换 OR-Tools / CBS / 强化学习，接口不用改。

## 2. 坐标处理：经纬度 → 局部米制平面

A* 需要"格子"，而经纬度是角度，直接离散化会出现"纬度 1 度 = 111km、经度 1 度 = 95km（在上海）"的各向异性，
搜索出的路径会被拉伸。做法是先投影到局部平面：

```
x = (lon - lon0) × 111320 × cos(lat0)      // 米
y = (lat - lat0) × 111320                  // 米
```

- 以**起点为原点**，几公里范围内误差可忽略（等距圆柱投影）；
- 规划完成后把栅格坐标转回经纬度；
- 需要绝对距离时用 haversine（球面大圆距离），与投影法互为校验。

> 为什么不直接用 pyproj/UTM？为了零依赖、可读、够用。真要做跨省市航线再引投影库。

## 3. 栅格化

```
外接矩形 = (起终点 + 「生效且落在航线走廊内」的障碍物包围盒) 再外扩 max(5 格, keepOutMargin/栅格)
grid_size_m = 50（可配）
```

> **为什么必须先做「航线走廊过滤」**：栅格外接矩形原本是「起点 + 终点 + 所有生效障碍物」的并集。
> 而系统的空域是**全国分布**的（上海 / 北京 / 深圳 / 成都各有禁飞区与建筑障碍），
> 于是一条上海市内 3km 的航线也会把北京、深圳的障碍物算进包围盒 —— 外接矩形被拉到国土尺度，
> 50m 栅格下栅格数高达上亿级，实测把算法服务内存吃到 7GB 后彻底卡死（所有派单失败）。
> 修复方式：只保留与「起点→终点 连线 ± 2000m（`ROUTE_CORRIDOR_M`）」相交的障碍物 —— 远离航线的
> 障碍物不可能影响本段航路；再加一道 `MAX_GRID_CELLS = 2_000_000` 的规模守卫，
> 超过就返回 `grid_too_large` 失败而不是分配超大数组。

- 栅格分辨率是**精度与耗时的旋钮**：50m 时一条 5km 航线约 100×100 格，A* 毫秒级出结果；
  调到 10m 会让格子数变 25 倍，扩展到几十万节点，需要重新评估。
- 起点/终点对齐到最近的栅格中心，最后再把首尾节点替换回**原始精确坐标**，
  避免"路径终点离目的地还有半格"。

## 4. 障碍物膨胀（keep-out margin）

不能把障碍物边界当可行走边界——无人机的定位有误差、机体有尺寸、风会吹偏。
所以把障碍物按 `keepOutMarginM`（默认 30m）向外膨胀，膨胀后的区域才算禁区。

- 圆：`radius + margin`
- 多边形：对每条边向外平移 `margin` 生成扩展多边形（MVP 用"点到边距离 + 顶点圆角"近似，
  比真正的 Minkowski 和简单，误差在安全侧）

**安全性原则：宁可多绕，不可少留。** 膨胀是"安全侧近似"，这是有意为之。

## 5. 高度维度怎么处理

低空空域是三维的，但 MVP 用了一个关键简化：**把高度当作"障碍物是否生效"的开关**。

```
若 altitude_m 不在 [min_altitude_m, max_altitude_m] 内 → 该障碍物对本次规划不生效
```

效果：

- 陆家嘴限飞区限制 0～60m，飞机在 80m 巡航 → 不构成障碍，可以飞过；
- 机场净空区 0～300m，80m 在其中 → 生效，必须绕开。

这样就以极低的复杂度实现了"升高一层就能穿过限飞区"这一真实规则。
真正的三维 A*（把高度也离散成层）留到需要多高度层调度时再做。

## 6. A* 细节

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 邻域 | 8 邻域 | 允许 45° 转向；直行代价 1，对角代价 √2 |
| 启发函数 | 欧氏距离 | 可采纳（admissible），保证最优性 |
| 开放列表 | `heapq` 最小堆 | `(f, counter, node)`，counter 用于打破 f 相同的比较 |
| 闭合集合 | `dict`/`set` | `g_score`、`came_from` 用字典 |
| 终止条件 | 弹出终点，或超过 `max_search_nodes`（默认 20 万） | 超限返回 `found=false, message="max_search_nodes_exceeded"` |

**为什么启发函数用欧氏距离而不是曼哈顿距离**：8 邻域下曼哈顿距离会高估对角方向的实际代价
（对角一步走 √2 的距离只花 √2 的代价，而曼哈顿算作 2），导致最优性被破坏。

## 7. 路径平滑（两级：视线法 + 转弯圆角化）

### 7.1 第一级：视线法（line-of-sight / string pulling）

栅格路径是"锯齿"的：8 邻域只能产生 0°/45°/90° 的方向，看起来像楼梯。
第一级平滑把几十个栅格台阶压成少量拐点：

```
从当前锚点出发，尽可能向后找一个最远的点，使"锚点→该点"的直线不穿过任何膨胀障碍；
把中间的点全部丢掉，以该点为新锚点继续。
```

- 平滑后**必须重新校验**（本项目复用同一张 `blocked` 栅格做超覆盖采样判定），
  否则可能把路径"抹"回障碍里——这是最典型的平滑 bug。
- 平滑后长度一定 ≤ 原路径，且只有首尾点保证不变。

### 7.2 第二级：转弯圆角化（新增）

第一级的结果仍然是**折线**——飞机在拐点瞬时转向。真实无人机做不到：它有最小转弯半径。
协调转弯的半径是

```
r = v² / (g · tan φ)
```

取巡航 15 m/s、倾斜角约 30°，得 `r ≈ 39.8 m`，因此取期望转弯半径 `TURN_RADIUS_M = 40 m`。

做法是逐拐点替换：对拐点 P 与前后点 A、B，沿 PA、PB 各退 `cut` 米得到切点 P1、P2，
以 P 为控制点作二次贝塞尔 `P1 → P → P2`，它就是在 P 处与两段相切的圆弧近似。
`cut` 同时被"相邻段长度的一半"夹住，保证相邻两个圆角不会重叠（否则航路会自己折回来）。

**安全兜底（关键）**：每条弧都用第一级同一张膨胀栅格**逐段校验**；
只要有一小段会蹭到膨胀障碍，就退回原来的尖角——宁可折一下，也不侵入禁飞区。

三个常量：

| 常量 | 值 | 说明 |
| --- | --- | --- |
| `TURN_RADIUS_M` | 40 m | 期望转弯半径，实际被相邻段长度的一半夹住 |
| `CORNER_SAMPLES` | 6 | 每个转弯用 6 段直线逼近圆弧；40 m 半径下弦高误差 < 0.2 m |
| `MIN_POINT_GAP_M` | 0.01 m | 去重阈值，避免切点拼接处出现零长度段 |

**代价与收益**：航路点数量增加（每个拐点约 +6 个），但远比第一级平滑**之前**的栅格路径少
（实测：同一绕障场景 39 → 16 个点），而且后端 `pointAtDistance` 是沿折线参数化的，
所以**飞机实际飞的轨迹与前端画的航线完全一致**——不会出现"画的是弧线、飞的是折线"。

## 8. 冲突检测

三类冲突，规则见 `docs/03-api-contract.md` 4.3 节，这里说设计取舍。

### 8.1 机-机：为什么要"外推"而不是只看当前位置

两架飞机此刻相距 200m 看起来没问题，但如果相向飞行，10 秒后就撞上了。
所以按各自航向与速度**匀速外推** `lookaheadSeconds`（默认 60s），以 1 秒为步长找最小间距。

- 水平间距与垂直间距**必须同时**小于阈值才算冲突：
  高度差 30m 的两架飞机水平重叠是安全的（不同高度层）；
- `closingSpeedMps` 用两机速度矢量在连线方向上的接近率，是判断"紧迫程度"的关键量；
- `timeToConflictS` 是首次突破阈值的时刻，可直接用于"还剩几秒处置"。

**MVP 的简化**：假设匀速直线。真实系统还要考虑转弯、加减速、风。

### 8.2 机-区：外推点也要判

只看当前位置不够——飞机可能还有 5 秒就进入禁飞区。外推点进入区域同样算冲突。

### 8.3 严重度分档

```
水平间距 < 0.5 × 阈值 → CRITICAL
水平间距 < 0.8 × 阈值 → HIGH
否则                  → MEDIUM
```

分档的意义是**决定处置优先级**：CRITICAL 要立即干预，MEDIUM 可以观察。

### 8.4 去重（在 Java 侧）

仿真每 5 拍检测一次，同一对飞机在 60 秒内只记一条。
指纹 = `冲突类型 : 机对(升序) : 区域`。
不做去重的话，10 分钟就能产生上万条重复记录，看板会被淹没。

> 指纹目前存在 Java 进程内存里，多实例部署时要挪到 Redis。

## 9. 性能

| 场景 | 规模 | 实测 |
| --- | --- | --- |
| 单次 A* 规划（50m 栅格，2 个障碍物，约 2km 航线） | 约 1000 个扩展节点 | 毫秒级（自检报告 6.65ms） |
| 冲突检测（10 架飞机 + 4 个区域） | 45 对 × 60 步外推 | 亚毫秒级 |
| 仿真 tick（50 个活动任务） | — | 取决于数据库往返，与算法无关 |

**瓶颈不在算法，在 Java 侧的数据库交互与 HTTP 往返。** 优化顺序应该是：

1. 批量取数据（现在每个任务单独查航路点，属 N+1）；
2. 合并冲突检测请求（已合并，一次请求带全部飞机）；
3. 算法侧缓存栅格化结果（同一起终点对、同一批障碍物可复用）。

## 10. 可调参数一览

| 参数 | 位置 | 默认 | 调整效果 |
| --- | --- | --- | --- |
| `gridSizeM` | 请求 / `sky.flight.grid-size-m` | 50 | 调小精度高、耗时长；调大反之 |
| `keepOutMarginM` | 请求 / `sky.flight.keep-out-margin-m` | 30 | 调大更安全、更容易绕远 |
| `defaultAltitudeM` | `sky.flight.default-altitude-m` | 80 | 决定哪些高度受限区域生效 |
| `maxSearchNodes` | 请求 | 200000 | 防雪崩的熔断阈值 |
| `smooth` | 请求 | true | 关闭可看到原始栅格锯齿路径（教学用） |
| `lookaheadSeconds` | `ConflictService` 常量 | 60 | 调大更早发现潜在冲突，误报也更多 |
| `minHorizontalSeparationM` | 同上 | 50 | 安全阈值，应按机型和空域分级配置 |

## 11. 后续演进

| 方向 | 说明 |
| --- | --- |
| 高度层分配 | 把高度离散成 60/80/100/120m 等层，机-机冲突可在垂直维度消解 |
| 冲突消解 | 现在只检测不解决。候选动作：调速、变高、等待、改航路 |
| 联合规划（MAPF） | 一次为多机规划互不冲突的路径（CBS / 优先级规划） |
| 动态障碍 | 临时管制区带时间窗，需要时空 A*（3D + 时间维） |
| 电量感知规划 | 把"能耗最小"作为代价函数，而不只是"距离最短" |
| 真实地形/建筑物 | 引入 DEM 高程数据与建筑轮廓，避障从二维升级到三维 |
